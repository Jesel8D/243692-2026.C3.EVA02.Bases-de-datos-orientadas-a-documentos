              Medición de métricas en bases documentales
                       Contención de CPU y memoria en agregaciones JSON:

                                MongoDB frente a PostgreSQL JSONB




 Objetivo
     Medir latencia, rendimiento y huella de recursos al ejecutar agregaciones JSON anidadas bajo límites
 estrictos de CPU (CFS throttling) y memoria con Docker cgroups v2, comparando un motor documental
 con un motor relacional que almacena documentos en JSONB.

 1. Preguntas sobre las métricas
M1 ¾Cómo cambian la latencia P95 y P99 de las agregaciones sobre documentos anidados cuando se
    limita de forma estricta la CPU y la memoria?
M2 ¾Qué motor usa de forma más e[U+001C]ciente los bu[U+001B]ers de ordenamiento y agrupamiento antes de volcar
    a disco temporal o fallar por falta de memoria (OOM)?
M3 ¾Cuál es la huella de CPU y memoria por cada 1 000 documentos procesados en el motor documental
    frente al motor con JSONB?

5. Cargas de trabajo (consultas)
5.1. Q1 [U+0016] Unwind, Filter & Grouping (saturación de CPU)
    Desanidar el arreglo de ítems, [U+001C]ltrar price >50, calcular subtotal (qty * price) y agrupar suma-
toria y promedio por país y categoría.
MongoDB (pipeline).

[
    { "$unwind": "$items" },
    { "$match": { "items.price": { "$gt": 50 } } },
    {
      "$group": {
        "_id": {
          "country": "$customer.geo.country",
          "category": "$items.category"
        },
        "total_revenue": { "$sum": { "$multiply": ["$items.qty", "$items.price"] } },
        "avg_revenue": { "$avg": { "$multiply": ["$items.qty", "$items.price"] } },
        "count": { "$sum": 1 }
      }
    }
]

PostgreSQL.

SELECT data->'customer'->'geo'->>'country' AS country,
      item->>'category' AS category,
      SUM((item->>'qty')::numeric * (item->>'price')::numeric) AS total_revenue,
      AVG((item->>'qty')::numeric * (item->>'price')::numeric) AS avg_revenue,
      COUNT(*) AS count
FROM orders, jsonb_array_elements(data->'items') AS item
WHERE (item->>'price')::numeric > 50
GROUP BY 1, 2;



5.2. Q2 [U+0016] Massive Sort & Top-K (estrés de bu[U+001B]er)
   Filtrar órdenes completadas en un rango de fechas, ordenar descendente por payment.final_total
y obtener el Top-1000 sin índices previos en el total.
Variantes de estrés de memoria.

    MongoDB: allowDiskUse: false / allowDiskUse: true
    PostgreSQL: SET work_mem = '4MB' / SET work_mem = '64MB'
MongoDB (pipeline).

[
    { "$match": {
        "payment.status": "completed",
        "timestamp": { "$gte": "2026-01-01T00:00:00Z" }
    } },
    { "$sort": { "payment.final_total": -1 } },


                                                           2
[U+000C]IT2iD                                                                              Bases de Datos en la Nube




    { "$limit": 1000 },
    { "$project": {
        "order_id": 1, "customer.id": 1, "payment.final_total": 1
    } }
]

PostgreSQL.

SELECT data->>'order_id' AS order_id,
      data->'customer'->>'id' AS customer_id,
      (data->'payment'->>'final_total')::numeric AS final_total
FROM orders
WHERE data->'payment'->>'status' = 'completed'
  AND (data->>'timestamp')::timestamptz >= '2026-01-01 00:00:00Z'
ORDER BY (data->'payment'->>'final_total')::numeric DESC
LIMIT 1000;
